1. Purpose & how to read this document
This is a build specification for a functional replica of the VirtualAccelerate platform (the SaaS currently used at
app.virtualaccelerate.com , where Finnpact operates a branch called "Finnpact LTD"). It was produced by
studying the running platform directly: navigating every module, inspecting the network/API layer, and reading the
live JSON data model through the platform's own API.
It is written so that a developer can build the replica from scratch. It covers:
  • What the platform is and the end-to-end business process it supports (Sections 2–5)
  • A module-by-module functional and UI specification (Section 6)
  • The data model and entity relationships (Section 7)
  • The API surface and conventions observed on the original (Section 8)
  • Authentication, roles and permissions (Section 9), i18n (Section 10), non-functional needs (Section 11)
  • The target technology stack and VPS deployment, chosen to match FinnPayments (Sections 12–13)
  • A phased delivery roadmap (Section 14) and appendices with the raw observed API catalogue, enumerations
    and field types (Section 15)

   Note on fidelity. Everything in Sections 2–9 is derived from the observed original system, so it is an accurate
   description of how the real product behaves and is structured. Sections 12–14 are the recommended implementation
   for your environment, not a copy of the original's internals (the original appears to be a Django/DRF backend; we are
   deliberately re-implementing on the FastAPI/React stack you already run, so it slots in beside FinnPayments).




2. Executive summary — what VirtualAccelerate is
VirtualAccelerate is a multi-tenant accelerator / incubator management platform. It runs the complete lifecycle
of an entrepreneurship support programme (an "accelerator" or grant/investment programme), from the moment an
entrepreneur applies through to selection, training, mentoring, graduation, and finally investment and portfolio
management.
In your case it is used to run OCIF ("Track I Support – 6/8 Months" and "Track II Support – 12 Months") cohorts of
Jordanian and regional startups: 80 applicants, 79 selected businesses, several cohorts, 12 training courses,
mentor evaluations, and an investment committee/portfolio pipeline.
It is best understood as the fusion of five products in one:
 1. An application & selection ATS — configurable public application forms, an applicant pipeline with custom
    stages, weighted scoring forms filled in by evaluators, and selection decisions.
 2. A learning management system (LMS) — multi-language courses with modules, lessons and video content,
    plus per-entrepreneur progress tracking.
 3. A mentoring & evaluation system — mentor assignment, mentor review question sets and conclusion
    question sets, evaluator scoring, and graduation decisions.
 4. An investment / deal-flow CRM — investment cases moving through deal-flow stages, multi-level approval
    committees, and portfolio management.
 5. A reporting & collaboration suite — a rich analytics dashboard, an investment reporting pack (portfolio
    snapshot, payments schedule, aging analysis, forex, and ~11 detailed financial sections), announcements, a
    shared calendar, a people directory, and in-app chat.
The whole thing is multi-tenant: an Organization owns one or more Branches, and virtually every record is scoped
to a branch ( organization_branch / branch_id ). Users switch the active branch from the top-left switcher.

Step by step:
 1. Apply. An entrepreneur submits a published Application Form tied to a Program. This creates an Applicant
   record (business + founder details) at the first selection stage.
 2. Select. In the Selection Board, staff/evaluators move applicants through configurable Stages (e.g. Track I
   Onboarding → Track I Support → Pitch Stage → Track II Onboarding → Track II Support). At relevant stages,
   evaluators complete a Scoring Form (weighted questions) producing an Average Evaluator Score. Applicant



                                        VirtualAccelerate — Replica Build Specification                      Page 4 of 18
   status is one of Invited, In Selection, Rejected, Archived. A registered flag tracks whether the founder has
   created their login.
 3. Enrol. Selected applicants become Businesses/Projects inside a Program (a cohort). The program bundles
   Courses, tracks course progress and course score, holds Mentor review questions and Mentor
   conclusion questions, and records a Graduation decision per business.
 4. Deliver. Entrepreneurs take assigned Courses (modules → lessons → video/content, with progress). Mentors
   are assigned and complete review/conclusion questions. Businesses accumulate scores.
 5. Invest. The Invest action promotes a business into the Investment track: a Deal-flow investment case
   progresses through Application → Evaluation → Pitching → Selection → Approved, is graded by tier (1–3) and
   round (Pre-seed … IPO), routed through multi-level Approval committees (statuses In Approval, Revision,
   Approved, Rejected), and finally managed in Portfolio management with full financial Reports.
Everything above is filtered/aggregated in the Dashboards and surfaced through Announcements, Calendar,
Directory and Chat for collaboration.



6. Module-by-module functional specification
For each module: purpose, key UI, features/actions, and the backing API (see Section 8/15 for the full endpoint
catalogue). All list endpoints are branch-scoped and paginated.

6.1 Dashboards / Analytics ( /dashboard/analytics )
Purpose: Program & portfolio analytics for the active branch.
UI: A greeting banner, then a tabbed dashboard with seven views: Program · Businesses/Projects · Investment ·
Learning · Team · Program Reports · Entrepreneur Learning Insights. A row of global filters sits at the top: Branch/
Org, Program, Application Year.
Program view (fully documented): a Businesses/Projects panel with filters (Stage of business/project, Industry,
Applicant age, Applicant gender, Country, Province, District) and:
  • A funnel bar chart: Applied / Selected / Graduated counts (e.g. 80 / 79 / 0).
  • Graduation rate (%), Selected businesses, Graduated businesses tiles.
  • Graduation time: min / average / max days.
  • Distribution breakdowns with counts: Stage of Business (Ideation, SGB, Startup), Industry (17 industries),
   Gender, Age band (<17, 18–24, 25–34, 35–44, 45–54, 55–64, 65+), Country / Province / District.
The other six tabs are analogous aggregations (investment metrics, learning/course completion, team, program-
level reports, and entrepreneur learning insights). Each is a read-only analytics view driven by its own dashboard
endpoint.
API: GET /dashboard-program/ , GET /dashboard-businesses/ (branch-scoped); plus reference lists for the
filters ( genders , business-types , business-industries , countries , program-list , applicants/{branch}/
application-years ).

Replica requirement: implement each dashboard view as an aggregation endpoint returning the counts/tiles/
breakdowns above; filters are query parameters. Charts: horizontal bar (funnel), donut (graduation rate), stat tiles,
and category-count lists.

6.3 Selection Board / Applicants ( /selections/investment-board )

6.4 Forms ( /forms )
Purpose: Build the Application Forms (what applicants fill in) and Scoring Forms (what evaluators score with).
Two sub-tabs: List of application forms and List of scoring forms.
Application form builder. A form has: name (multi-language), main language, description, a linked Program, a
status (Draft/Published), and an ordered list of fields. Each field has a field type, is_required , order , multi-
language label, and (for choice types) options. Observed field types:

 Field type              code_name                     Behaviour

 Header                   header                       Section heading / non-input divider

 Input                    input                        Free text input

 Poll                     poll                         Single choice (radio) with options

 Multiply Poll            multi_poll                   Multiple choice (checkboxes) with options

 Spinner                  spinner                      Dropdown/select with options


   The replica should also support file upload, date, number, and long text field types (needed for real onboarding
   forms — e.g. document uploads for "Identity Card or Passport"). Treat the five observed types as the minimum and

Also on the Forms screen: Manage channels (application source channels) and Manage subindustries (taxonomy

Scoring form builder. A scoring form is tied to a Program and a selection stage, has an is_for_graduation

API: GET/POST /application-forms/{branch}/ , GET /application-forms/{branch}/{id}/ , GET/POST /
scoring-forms/{branch}/ , GET /scoring-forms/{branch}/{id}/ , GET /form-statuses/ .

892348233054 ); on the replica use standard auto-increment or UUID/BIGINT — see Section 12. OB =

8. API design & conventions
The replica's API should mirror the original's shape so the React client can be ported with minimal change.
Observed conventions:
  • Base path & i18n prefix: /{lang}/api/… (e.g. /en/api/programs/… ). The language segment selects
   response localisation. Keep this: route /{lang}/api/... and use lang for i18n of enum/labels.
  • Versioning: a mix of unversioned ( /api/… ) and /api/v2/… for newer/paginated list endpoints (applicants,
   users, program businesses). Adopt /api/v2/ for list endpoints with pagination/filtering.
  • Tenancy in the path: branch id is a path segment on branch-scoped resources ( /api/programs/
   {branch_id}/… ) — the server must still authorise that the caller may access that branch.
  • Pagination: ?page=&page_size= (DRF-style). Responses for v2 lists are {count, next, previous,
   results[]} (implement the same envelope). page_size=1000000 is used to fetch "all" for exports — provide a
   proper export endpoint instead in the replica to avoid unbounded queries.
  • Filtering/search: query params ( search , business_name , type , ordering , plus domain filters).
  • Errors: DRF-style — {"detail": "..."} with appropriate status (e.g. 401/403 "You do not have permission to
   perform this action.").
  • Statuses/enums as objects: returned as {id, name, code_name} (client filters on code_name ).
  • Nested reads: detail endpoints return nested children (course → modules → lessons → content; form → fields
   → options) — convenient for the SPA; replicate.
The full observed endpoint catalogue is in Appendix 15.1.



9. Authentication & authorization

9.1 Mechanism (observed)
  • JWT (HS256) access token + refresh token, stored in the browser's localStorage ( accessToken ,
    refreshToken ), plus currentBranchId and a userData blob.
  • Requests authenticate with Authorization: Bearer <accessToken> .
  • Login exchanges credentials for the token pair; a refresh endpoint issues new access tokens.




                                       VirtualAccelerate — Replica Build Specification                    Page 11 of 18
  ⚠️   Security defect in the original — do NOT replicate. The original's JWT payload contains the user's
  password (alongside user_id and an expiry). That is a serious flaw: JWT payloads are only base64-encoded (not
  encrypted), so anyone who reads the token reads the password. In the replica: never put the password (or any
  secret) in the JWT. Put only user_id , branch_id /roles, token type, and expiry. Store password hashes only
  (argon2/bcrypt). Prefer httpOnly, Secure, SameSite cookies for the refresh token over localStorage to reduce
  XSS exposure; keep the short-lived access token in memory. This is the single most important correction to make
  versus the original.


9.2 Authorization (RBAC)
 • Roles are branch-scoped with code_name ( branch_admin, organization_admin, entrepreneur, mentor,
  investment_manager , + custom). Some are is_constant (cannot be deleted).
 • Permissions are granular and assigned per role via Manage roles — every module/action should map to a
  permission (e.g. programs.view , programs.edit , applicants.score , investment.approve ,
   users.manage , reports.view , …). The API must enforce them server-side, not just hide UI.
 • Every request is authorised on two axes: (a) does the user's role grant the capability, and (b) may the user
  act within the target branch_id (tenant isolation).
 • The default landing/experience differs by role (staff dashboard vs entrepreneur portal).



10. Internationalization (i18n)
 • UI language switcher in the top bar; API takes a /{lang}/ path segment.
 • Content is multilingual at the field level: form/field/option names carry per-language columns — observed
  suffixes: _en, _ru, _uz, _ky, _tg, _ur, _ar, _fa, _pt (English, Russian, Uzbek, Kyrgyz, Tajik, Urdu,
  Persian/Farsi, Portuguese) plus a main_language . Courses carry a language and subtitle_languages[] .
 • RTL support required (Arabic, Urdu, Farsi are present in real data).
 • Replica requirement: store translatable strings as per-language columns or a translations table; the React app
  uses an i18n library (e.g. react-i18next ); the FastAPI layer returns the requested language's variant and falls
  back to main_language .



11. Non-functional requirements
 • Multi-tenancy & isolation: strict per-branch scoping and authorization on every query.
 • File storage: documents, business files, course videos, logos/photos. Videos are large — store on disk (or
  object storage) and stream; do not put binaries in the DB. Serve via nginx X-Accel-Redirect or signed URLs.
 • Exports: Excel export on programmes and all reports.
 • Pagination everywhere for lists (some branches have 100+ users, 80+ applicants).
 • Real-time for chat and notifications (WebSocket recommended).
 • Observability: the original uses Sentry (React SDK) for error tracking — keep an equivalent (self-hosted
  GlitchTip/Sentry or logs).
 • Audit trail for selection decisions, scoring, graduation, and investment approvals (governance).
 • Performance: dashboard aggregations should be indexed/materialised; avoid page_size=1000000 scans.
 • Backups: since data includes grant/investment records, schedule DB + file backups.
 • Security: HTTPS only (Certbot), input validation (pydantic), rate-limiting on auth, RBAC enforced server-side,
  secrets in env not code, and the JWT correction from §9.1.
